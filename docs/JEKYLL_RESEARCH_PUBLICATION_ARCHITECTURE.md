# Jekyll Research Publication Architecture

Status: **production-ready source and build architecture; Pages source switch externally gated**

```text
Scientific computation
Python / JAX / SciPy / NetworkX / optimization
        ↓
Scientific outputs
JSON / CSV / SVG / validated metadata
        ↓
Knowledge model
Markdown / YAML / JSON
        ↓
Jekyll 4.4.1 + Liquid + Collections
        ↓
MathJax / SVG-D3 / Three.js
        ↓
TypeScript / JavaScript
        ↓
source verification
        ↓
rendered-artifact verification
        ↓
GitHub Pages artifact deployment
```

## Governing boundary

**Scientific truth is not publication representation.**

- Python and numerical libraries compute scientific results.
- YAML, JSON, and Markdown preserve research knowledge and provenance.
- Jekyll organizes scholarly content and relationships.
- MathJax typesets mathematics.
- D3/SVG renders 2D scientific visualization.
- Three.js/WebGL renders 3D scientific geometry.
- TypeScript manages browser interaction and state.
- GitHub Actions verifies the source and rendered artifact before deployment.

## Production invariants

1. `index.html` and `lab.html` remain the canonical legacy-compatible public routes and are copied unchanged by Jekyll.
2. Seven research-stage pages, model pages, experiment pages, and figure-provenance pages are generated by Jekyll collections.
3. `_data/` is build-time publication metadata; `assets/data/` is browser-facing runtime scientific data.
4. The rendered artifact must preserve the governed Light Sky Blue / Deep Sky Blue accent system and the no-gold invariant.
5. A scientific artifact must distinguish model, dataset, experiment, provenance, verification state, and claim scope.
6. The pinned production builder is Jekyll 4.4.1 through Bundler.
7. Deployment uses the GitHub Pages artifact protocol only when the repository Pages source is configured for GitHub Actions.

## Why `.nojekyll` remains in the source repository

The current repository-level Pages configuration is still the legacy branch-publishing mode. Removing `.nojekyll` before changing that account-level setting would silently hand production to GitHub's legacy Jekyll environment rather than the pinned Jekyll 4.4.1 workflow.

Therefore `.nojekyll` remains as a **legacy-source safety interlock**. It is not included in the generated `_site` artifact, and the rendered-artifact verifier fails if it appears there.

Once **Settings → Pages → Build and deployment → Source = GitHub Actions**, the `pages-jekyll.yml` workflow automatically becomes authoritative on the next push to `main` or manual dispatch.

## Required validation gates

Before a Pages artifact can be uploaded:

1. existing scientific/visual source verification must pass;
2. Jekyll 4.4.1 must build without error;
3. homepage and lab route semantics must remain present;
4. all seven stage routes must exist;
5. model, experiment, and figure provenance routes must exist;
6. runtime data JSON must satisfy the publication boundary checks;
7. the research publication stylesheet must preserve the no-gold RGB contract.

This architecture deliberately separates **repository merge readiness** from **account-level Pages-source authority**.
